核对日期：2026年11月23日。本文对应当前食物库发布流程及新版 App 的分类更新功能。

## 1. 现在如何工作

食物数据在独立的 GitHub 仓库维护，发布后由手机下载安装到本地。搜索、分类浏览、分量换算和记餐使用本地数据，不会每次搜索都请求网络。

```text
修改食品源文件、分类配置
  → 本地构建和校验
  → 提交到数据仓库 main
  → 手动运行 Publish food catalog
  → 工作流验证 CDN 文件后发布版本通知
  → App 检查版本、下载和校验
  → 食物与分类一起切换为新版，离线继续可用
```

当前采用整库更新，不是增量更新。App 安装包仍带有基础食物库，下载的新版本也会保存在手机本地。因此，云端更新解决的是“修改数据不用重新安装 App”，目前没有取消安装包内的食物库。

## 2. 哪些文件需要维护

| 文件 | 用途 | 维护方式 |
| --- | --- | --- |
| `source/foods.jsonl` | 食品源数据，一行一个 JSON 对象 | 新增食品、修正名称、别名、营养和分量时修改 |
| `source/categories.json` | 分类名称、顺序、归类规则及人工修正 | 调整左侧分类栏和食物归属时修改 |

| `tools/validate_catalog.py` | 校验生成的目录 | 每次发布前运行 |
| `tools/test_categories.py` | 分类相关回归测试 | 修改分类后运行 |
| `dist/catalog.json` | App 实际下载的完整目录 | 由构建脚本生成，不手工编辑 |

目前没有单独的网页后台，维护入口是这些文件和 GitHub Actions。

## 3. 如何修改食物

在 `source/foods.jsonl` 中找到对应记录，保持一行一个完整 JSON 对象，使用 UTF-8 保存。

常用字段：

| 字段 | 含义与要求 |
| --- | --- |
| `id` | 稳定的食物 ID。已有食品不因改名、调分类或修营养而更换 ID |
| `name`、`brand` | 食物名称和品牌。保留必要的生熟、干湿、含糖状态等区别 |
| `aliases` | 别名数组，用于补充检索名称 |
| `unit` | 营养基准单位，当前为 `g` 或 `ml` |
| `nutrients` | 每 100 g 或每 100 ml 的营养值，取决于 `unit` |
| `portions` | 已知分量，包含 `label` 和 `grams`。只填有依据的规格 |
| `category` | 原始分类文字，由分类配置映射到最终侧栏分类 |
| `sources`、`nutrition_source` | 数据来源及营养值出处，供追溯使用 |
| `weight_basis` | 原数据中的重量基准信息，保留有效信息 |
| `revision` | 构建时根据食物内容生成，不需要手工填写 |

营养字段示例：`energy_kcal` 是千卡，`protein_g`、`carbohydrate_g`、`fat_g` 是克，`sodium_mg` 是毫克。不要把包装上的每份值直接当作每 100 g 值写入。

分量示例：

```json
"portions": [
  {"label": "小个", "grams": 40},
  {"label": "中等", "grams": 50},
  {"label": "大个", "grams": 60}
]
```

同一食品不重复维护相同重量，例如已经有“中等 50 g”，不要再增加“50克”作为另一份量。同一食品内的分量重量必须唯一、为正数，且不超过 10,000。

克重和容量不能随意互换。`unit: "ml"` 表示每 100 ml 的营养基准；不要把毫升数填入 `portions.grams` 假装是克重。没有可靠重量或密度依据时，不增加推测分量。

新增食品需要分配一个从未使用过的唯一 ID，并保留来源。当前脚本不会自动做跨库合并或语义去重；录入前仍需核对名称、品牌、生熟状态、营养基准和已有记录。不要按名称相同直接合并，也不要用相似食品的营养值代替未确认数据。

不要把旧 ID 分配给另一种食品。已在历史记录、个人映射或收藏中使用的 ID 应尽量保留；若确需删除，应先评估这些引用。

## 4. 如何修改分类

修改 `source/categories.json`。分类与食品都在同一个目录快照中发布，手机不会先换分类、再慢慢补食物。

当前分类：主食、蔬菜、水果、肉蛋奶、水产、豆类坚果、零食饮料、中西菜肴、油脂调味、其他。

### 改名称或顺序

`categories` 数组控制侧栏显示顺序；其中的 `label` 控制中文名称。已有分类的 `id` 尽量保持不变。

例如，下列配置会先显示“水果”，再显示“蔬菜”。这是局部示例，不要覆盖整个配置：

```json
"categories": [
  {"id": "fruits", "label": "水果"},
  {"id": "vegetables", "label": "蔬菜"}
]
```

新增分类时，在完整数组中增加唯一 ID 和名称，并补充规则或人工归属。当前最多支持 64 类，名称最长 24 个字符，必须保留兜底分类 `other`。删除分类前，需要清理所有指向该分类的规则和映射。

### 单独修正某个食物的分类

在 `overrides` 中填写“真实食物 ID → 分类 ID”。这是最适合少量纠错的方式，优先级最高。

```json
"overrides": {
  "这里替换为食物的真实ID": "staples"
}
```

上面只是格式示例，不能把占位文字直接写入配置。构建会检查 override 引用的食物是否存在。

### 批量归类

- `source_categories`：把原始分类文字映射到侧栏分类。
- `rules`：按食物名称的正则表达式归类；同级规则按数组顺序匹配。

当前执行顺序为：

1. 按食物 ID 的 `overrides` 人工指定。
2. 名称规则中明确指向“油脂调味、零食饮料、中西菜肴”的结果。
3. `source_categories` 中的原始分类映射。
4. 其余名称规则。
5. 无法判断的归入 `other`。

例如，原始分类为谷类的蛋糕可以归入零食，名称为番茄炒饭的食品可以归入中西菜肴。若规则误判，用 ID override 修正更稳妥，不必为一个特殊食品扩大通用规则。

只修改食品和分类数据，不涉及新数据格式或新交互时，无需重新构建 APK。

## 5. 一次标准更新怎么发布

### 第一步：同步并修改源文件

以下命令在 PowerShell 执行。先检查工作区；存在未保存修改时，先处理它们再同步。

```powershell
Set-Location 'C:\Users\Administrator\Documents\ChatGPT\吃有数\chiyoushu-food-data'
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data status --short
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data pull --ff-only origin main
```

根据需要编辑 `source/foods.jsonl` 和／或 `source/categories.json`。

### 第二步：本地构建并校验

在同一个目录执行，Python 3 即可，相关脚本使用标准库：

```powershell
python tools/build_catalog.py
python tools/validate_catalog.py
python tools/test_categories.py
```

每条命令都要成功退出，再继续。构建会显示食物数量、字节数和 SHA-256；校验失败时先修正源文件，不发布。

现有校验覆盖 ID 唯一、分类引用、营养值有效范围、分量重量重复和文件上限等结构问题，不代表所有营养值都经过权威核实。食品生熟状态、配方及数据依据仍需维护者核对。

### 第三步：提交到 main

确认差异只包含本次需要发布的内容，再执行：

```powershell
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data diff --stat
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data add source/foods.jsonl source/categories.json dist/catalog.json
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data commit -m "更新食物数据与分类"
git -c safe.directory=C:/Users/Administrator/Documents/ChatGPT/吃有数/chiyoushu-food-data push origin HEAD:main
```

### 第四步：启动发布工作流

1. 打开数据仓库的 **Actions**。
2. 选择 **Publish food catalog**。
3. 点击 **Run workflow**，分支选择 **main**。
4. 等待整个工作流成功，尤其是 CDN 下载验证和 Pages 部署步骤。

工作流地址：<https://github.com/daoshi818-crypto/chiyoushu-food-data/actions/workflows/publish.yml>

**仅提交或 push 不会发布食物库更新。** 当前食物库工作流需要手动启动。仅修改维护文档则不需要启动发布。

工作流会重新生成和校验目录，必要时提交生成文件；然后从固定 Git 提交的 CDN 地址实际下载目录，核对大小和 SHA-256，最后才发布版本通知。无需手工填写 hash、目录版本或发布序号。

### 第五步：在手机上验收

进入 **设置 → 数据 → 食品数据库 → 检查更新**。

确认版本变化，并检查本次修改的食品、分类和分量。更新成功后可以立即使用；断网后再次搜索，确认仍能正常读取。

## 6. 手机何时更新、如何保护现有数据

- 进入主界面、App 返回前台时尝试检查；主界面在前台时，每 10 分钟也会尝试触发一次。
- 成功检查后通常间隔约 60～65 分钟才再次请求；初始间隔为 60 分钟。不是在后台持续每小时下载。
- 自动检查失败后，最短 5 分钟后才允许再次尝试；实际还要等下一个触发时机。
- 手动“检查更新”可跳过上述自动检查间隔，但仍有 10 秒的防重复请求限制。
- 有新版才整库下载。下载后验证文件大小、SHA-256、食品数量、数据结构及分类引用，全部通过后才激活。
- 更新失败继续使用当前有效数据。保存当前和上一有效下载版本；启动时当前版本损坏会尝试上一版，都不可用则回到安装包内基础库。
- 更新公共库不会重新计算并覆盖已经保存的历史饮食快照，也不把个人记录、自定义食物或 AI 密钥上传到公共数据仓库。

更新过程中需要联网；日常搜索和记餐不依赖云端实时响应。


完整目录优先使用固定提交的 jsDelivr 地址，失败后尝试 GitHub Raw：

```text

https://raw.githubusercontent.com/daoshi818-crypto/chiyoushu-food-data/<source_commit>/dist/catalog.json
```

`<source_commit>` 取自版本通知，不使用可变的 `@main` 作为手机正式目录地址。

| 字段 | 用途 |
| --- | --- |
| `release_seq` | 单调递增的发布序号，当前来自工作流运行编号 |
| `catalog_version` | 展示用版本，例如 `2026.11.23.4` |
| `source_commit` | 本次目录所在的完整 Git 提交 ID |
| `file.sha256` | 完整性校验值 |
| `file.bytes` | 精确文件字节数 |
| `file.food_count` | 食物条目数量 |
| `catalog_schema_version` | App 支持的数据格式版本 |

当前目录上限是 15 MiB，现有目录约 9.80 MiB。接近上限时需要评估压缩、拆分或增量方案，不能直接无限追加。

GitHub Pages、jsDelivr 和 GitHub Raw 在中国大陆的可用性和速度会随网络变化，当前方案不能承诺稳定高速。离线缓存用于保证已安装数据可继续使用。当前仓库、通知域名及下载地址规则固定在 App 代码中；更换这些地址需要同步修改 App，或先增加可配置机制。

## 8. 发布后发现问题怎么回滚

把源文件恢复到正确内容，然后按正常步骤重新构建、校验、提交并发布，生成更高的 `release_seq`。

不要直接把线上版本通知换成旧序号。App 会拒绝低于当前版本的序号，也会拒绝“序号相同但内容不同”的通知。需要重试失败发布时，若旧序号已经对外生效，启动一次新的工作流运行，不复用旧序号。

本机上一版缓存用于损坏恢复，不等于给所有用户主动回滚；云端纠错仍需要发布一个新版本。

## 9. 常见问题

| 现象 | 检查方式 |
| --- | --- |
| GitHub 已修改，手机没变化 | 确认提交在 main，并已手动运行 Publish food catalog；检查整个工作流结果 |
| 工作流卡在 CDN 验证 | 查看该步骤日志；通知尚未发布时，手机仍使用旧版，不要跳过校验 |
| 手机显示更新失败 | 检查网络及 Pages 通知、CDN 文件是否可访问，稍后手动重试，现有离线库可继续用 |
| 新分类没出现在侧栏 | 确认已安装支持侧栏的新 App，并成功下载包含分类的新版目录 |
| 某个食品分类不对 | 查真实 ID，在 categories.json 的 overrides 修正，重新发布 |
| 分量选项重复 | 检查同一食品 portions 内是否有相同 grams，保留准确、易懂的规格名称 |
| 改营养后历史记录没变化 | 历史记录保留保存时的快照；公共库更新主要影响之后选择和录入的数据 |

**食物库更新与 App 更新是两条流程：** 修改食品、分类走本说明；界面、算法、功能和安装包版本变更走 App 仓库的 APK 构建发布流程。不要为一次分类纠错额外构建 APK。
